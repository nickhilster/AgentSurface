# Use AgentSurface in a Website Repository

This guide is for a coding agent working in a website repository. Use it to make the website easier for ordinary web-capable agents to search, while preserving its existing human experience. Follow the target repository's own `AGENTS.md`, `OPERATE.md`, contribution guide, and security rules first.

AgentSurface's detailed product contract is in [`docs/SPEC.md`](docs/SPEC.md) and [`docs/superpowers/specs/2026-10-19-repo-to-agent-surface-design.md`](docs/superpowers/specs/2026-10-19-repo-to-agent-surface-design.md).

## Desired result

Add or improve a site-native discovery page that lets a browser-capable agent find a small number of relevant public items and link each result to its exact canonical first-party detail page. The website's actual item page remains the full user experience.

The target repository is the source of truth. Do not require a separate OpenAPI document, public API, MCP server, or host-specific adapter when the repository already contains usable data access.

## Workflow

### 1. Learn the repository before changing it

Inspect:

- framework, routes, rendering mode, and local run/test/build commands;
- product, inventory, service, or content models and the code that reads them;
- which fields are public and where publication/authorization boundaries are enforced;
- how an individual entity maps to its real detail route;
- existing search/filter behavior, pagination, caching, freshness, locale, and market rules;
- existing agent instructions and generated-file ownership rules.

Use source code, schemas, tests, and local behavior as evidence. Do not infer product data from labels or invent a new backend because the source is unfamiliar.

If the `agentsurface` CLI is available but `.agentsurface/config.yaml` is missing, initialize it using verified site facts:

```sh
agentsurface init --repo <website-repo> --name "<verified-site-name>" [--hostnames <verified-hostname>]
```

Do not invent hostnames. `init` refuses to overwrite an existing config; inspect that config and preserve its owner decisions.

If the `agentsurface` CLI is available, run:

```sh
agentsurface inspect --repo <website-repo>
```

Read `.agentsurface/model/` and its `unknowns`; treat the model as an index to verify against source code. The CLI currently inspects routes/capabilities and configured catalog sources. It does not yet implement a tailored discovery page for the target website.

### 2. Map the item identity to its exact page

For each supported result type, identify:

- a stable source ID;
- the authoritative fields suitable for matching and showing publicly;
- the route generated by the site's router or source record;
- whether the route identifies a unique item, variant, or inventory unit.

Test representative routes. A category page, model-family page, or generic search URL is not an exact item destination when the source has an individual listing. If exact identity-to-route mapping cannot be verified, report the gap and do not fabricate a URL.

### 3. Choose the smallest site-native implementation

Reuse the site's existing data access and route structure.

- For a small static collection, use its existing structured files and a bounded static discovery page.
- For a CMS or dynamic catalogue, use the existing server-side query/data path and render a bounded result set.
- Keep the surface an ordinary accessible web page with meaningful HTML, visible labels, keyboard-operable controls, URLs, and normal links.
- Use supported search terms/filters only. Prefer reproducible GET-based query state where it fits the site.
- Include only fields needed to find and assess candidates. Keep the site's full product experience on its existing detail pages.
- Structured metadata such as Schema.org Product/ItemList may supplement the page; it does not replace readable results or prove data freshness.

Do not add an entire-catalogue response for a narrow query. Do not expose private fields, bypass auth/tenant rules, transmit user profile data, or add seller/contact/checkout actions.

### 4. Implement and verify

Make a focused, reviewable change in the website repository. Follow its current patterns and preserve existing human flows and owner-managed files. Do not deploy, publish, or configure an external service as part of this workflow unless separately requested.

Run the target repository's relevant tests, build, and lint checks. Start a local preview when feasible and verify:

- supported queries return a small useful set;
- each result's fields match its authoritative source;
- each result link opens the exact item page and the page identifies that same item;
- empty, unsupported, missing, or stale data is represented honestly;
- public/private boundaries still hold;
- the existing human experience still builds and works.

If the `agentsurface` CLI is available, run validation after the change:

```sh
agentsurface validate --repo <website-repo> --no-drift-check
```

Use `--server <preview-url>` instead of `--no-drift-check` when a local site is running and live route/content checks are needed. `agentsurface generate` currently generates configured Markdown/discovery artifacts; it does not generate the site's catalogue search page.

### 5. Report the result

Summarize:

- the data source and route mapping you verified;
- which files you changed and how the discovery page works;
- representative exact item URLs and how you checked them;
- tests/build/lint/preview commands and results;
- freshness, missing-data, privacy, or market limitations;
- any unresolved owner decision.

Separate verified behavior from unknowns. Do not claim dynamic inventory, broad framework support, or in-app browser support based on a static fixture or a successful build alone.

## AgentSurface CLI reference

Available commands in the current project:

```text
agentsurface init
agentsurface inspect
agentsurface generate --server <url>
agentsurface validate [--server <url> | --no-drift-check]
agentsurface diff [--server <url>]
agentsurface catalog-manifest
agentsurface-mcp
```

`init` creates AgentSurface config. `inspect` writes the canonical model. `generate` and `validate` may need a running site URL for render/drift checks. `diff` previews generated artifact changes. `catalog-manifest` and `agentsurface-mcp` are optional catalog projections. Use only commands relevant to the repository task; the website discovery implementation itself should use the site's source and ordinary web conventions.
