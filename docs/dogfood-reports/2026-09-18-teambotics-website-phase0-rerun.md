# Dogfood Re-run 2026-09-18 (Phase 0 review follow-up)

Target repo: teambotics-website (main site), same target as the original run.
AgentSurface version/commit: post-review fix on top of `de8ce75`, before this commit.

## Why this run happened

A review of `de8ce75` (Phase 0, plan §1.1–§1.8) found that the §1.1 fix — deriving
`llms.txt`'s capabilities section from `CapabilityRecord[]` instead of a hardcoded
`/api/values` claim — introduced two regressions, both caught by re-running the real
adapter against a hand-built fixture rather than trusting `generate.test.ts`'s existing
fixtures:

1. Capabilities with `authRequired: true` were published in the public `llms.txt` with no
   filter — a real leak of auth-gated endpoint existence, against `docs/SPEC.md`'s
   "Generated discovery must not expose otherwise undiscoverable private resources."
2. The generated link pointed at `c.backingImplementation` (a source file path, e.g.
   `app/api/values/route.ts`) instead of `c.name` (the actual route path) — a dead link
   that also disclosed internal repo file layout.

The review also found `generate.test.ts`'s capability fixture didn't match the shape
`NextAppRouterAdapter.inspectCapabilities` actually emits (wrong field values), which is
why the tests passed while both bugs were live, and asked for the full dogfood sequence
to be re-run against the real target repo to prove the fix rather than assert it.

## What was fixed

In `src/commands/generate.ts`'s `generateLlmsTxt`:

- Capabilities are now filtered on `backingImplementation !== null && !c.authRequired`.
- Capability links now use `c.name` (route path) as both label and link target, never
  `c.backingImplementation`.

`generate.test.ts`'s capability fixture was rewritten to match the real adapter's actual
field shape (`name: "/api/values"`, `backingImplementation: "app/api/values/route.ts"`,
`authRequired` derived from the first path segment), and three tests were added:
capability listing uses real values, links use `c.name` not the source path, and an
`authRequired: true` capability (mirroring the real `/api/admin/login` record) is
excluded entirely.

Separately, `src/cli/index.ts`'s `generate` command no longer defaults `--server` to
`http://localhost:3000` — a Next.js-specific default inside otherwise framework-agnostic
code (§1.3). It now requires `--server <url>` explicitly and exits non-zero with an
actionable message if omitted.

## The real re-run

Ran the actual CLI (`dist/cli/index.js`) against `/c/DEV/teambotics-website` with a real
`next dev` instance serving on port 3101 — not a fixture.

**`inspect`**: 41 routes, 25 capabilities — same counts as the original 2026-09-18 run.
Confirmed directly from `capabilities.json`: **18 of the 25 real capabilities have
`authRequired: true`** (all under `/api/admin/**`), including
`{"name":"/api/admin/login","backingImplementation":"app/api/admin/login/route.ts","authRequired":true}`
— exactly the record the review used to demonstrate the leak.

**`generate`** (with the fix applied, run twice: once against the stale pre-existing
`public/llms.txt` from the original run, which correctly triggered an ownership conflict
and was not overwritten; once after removing that stale file, to inspect fresh output):

- Page generation output unchanged from the original run: 18 pages generated, the same
  21 skips with the same reasons (dynamic routes, `authenticated`/`private-internal`
  classifications, `BOSS/**` and `/nonprofit-application`'s missing content boundary).
- New `llms.txt`, diffed against the pre-fix file:
  - `grep -ic "admin"` on the new file: **0 matches**. All 18 admin capabilities are
    excluded — the leak the review found is closed on the real target, not just in a
    fixture.
  - `grep -c "app/api"` on the new file: **0 matches**. No source file path appears
    anywhere in the output.
  - The 7 remaining (non-admin, non-null-backing) capabilities are listed, each linked by
    its real route path, e.g. `- [/api/values](/api/values): API route at /api/values` —
    a link that actually resolves, not a dead link into the repo's file tree.
  - Format is now spec-conformant (`[label](/path.md)`, no `— Markdown:` suffix), matching
    the §1.7 fix from the original Phase 0 commit, which this run also re-confirmed still
    holds.
- `generate` with no `--server` now fails fast (`"generate" requires --server <url>..."`,
  exit code 1) instead of silently defaulting to `localhost:3000`.

**`validate --server http://127.0.0.1:3101`**: 18 generated files checked, 18 discovery
links checked, zero failures.

## One thing this run surfaced, not a defect

The pre-existing `public/llms.txt` from the original 2026-09-18 run used the old,
single-line ownership header format (`<!-- Generated by AgentSurface. ... -->`), which
predates the current multi-line header (`ownershipHeader()` in `src/lib/ownership.ts`).
The new ownership check correctly did not recognize it as AgentSurface-owned and refused
to overwrite it on the first attempt in this run. This is the ownership-safety mechanism
working as designed — it just means any repo carrying `llms.txt`/page output generated by
a pre-Phase-0 AgentSurface build will need that one file manually cleared (or
`ownership.overwriteHumanOwned` set) once, on upgrade. Worth a line in a future changelog,
not a code fix.
